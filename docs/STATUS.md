## Mechanisms

Labels: **tested** = code on main with automated tests; **demo** = code runs, but not in the intended deployment (fixture keys, loopback instead of Tor, in-memory state); **specified** = designed, no code; **future** = direction only.

### Catalog

| Mechanism | Status | Notes |
|---|---|---|
| Signed store and listing records, canonical encoding, BIP 340 signatures | tested | Encode, decode, sign, verify; tamper tests. |
| Listing address = SHA-256 of body | tested | Order letters commit to it. |
| Vendor content self-labels (rating, tags) in the signed body | tested | Store v2, listing v5; unlabeled v1/v4 still decode. |
| Listing v6: stable id, images, fiat price | tested | A random 16-byte id kept across edits, up to 8 image hashes, and an optional fiat price (USD, EUR, GBP, JPY in minor units, plus shipping) beside the signed sats price. The seller's node converts the fiat price at its rate when an order arrives and falls back to the signed sats price without one; the buyer refuses terms more than a quarter above what checkout showed. v4/v5 still decode. |
| Listing authoring | tested | `POST /store/listings`, `PUT` and `DELETE /store/listings/{id}`, kept in `own-listings.obv` with each listing's earlier addresses, so an order against an older version still prices. Spend tier: `423` while locked. A paid sale takes its units off the shelf, and the listing is signed again with that count. |
| Storefront editor and role | tested | `GET`/`PUT /store/profile` (name, tagline, about, avatar and banner from `POST /media`, region, ships-to, policies) signs the store record again, and every listing when the name changes; `setUp` is true once saved. `PUT /store/role` keeps the onboarding choice (buyer or seller) outside any signed record. Monero and escrow are not offered for the own store yet. |
| Store record v3: mailbox key, onion, accepted moderators, public profile | tested | Tagline, about, avatar and banner as SHA-256 hashes, shipping/returns/processing policies, ships-to country codes, created-on date. v1/v2 still decode; one canonical encoding; every field tamper-tested. |
| Store pages and store media for the paired client | tested | `GET /stores`, `GET /stores/{key}`, `GET /media/{hash}` (PNG/JPEG/GIF/WebP, 2 MiB cap, served only if the bytes hash to the name). |
| Client verifies signed records | tested | `@noble/curves` BIP 340 over each store and listing record; headers are built from the signed bytes; a listing that fails, or whose store is not a verified store, is dropped and counted. |
| Third-party labeler sets (`OBLB`) | tested | Signed, sequenced, retractable. Node fetches only from a built-in sample labeler or a loopback URL; no Tor. |
| Client safe mode and keyword filter | tested | Runs on the device only. |
| Catalog served to client | demo | Testnet4 only: three demo stores (Marlow Goods, Hale Paper, North Kitchen), each with its own fixture key and v3 record, signing its own listings (38 in all), plus the node's own store and followed stores. Mainnet serves only the node's own store. |
| Following stores on other nodes | demo | `POST /follows {url}` (loopback HTTP, as escrow mail). The node reads `GET {url}/public/store` (no token, no `Origin`, only while the user sells), checks every signature, copies the images, and keeps the copies in `replicas.obv`, so a seller that is offline stays browsable and orderable. A copy never replaces the own store or a demo store. The desktop node keeps its port in `node.port`, so a follow survives restarts. |
| Replication by every node | specified | Only stores a node follows are copied; no gossip. |
| Publishing cost against spam | tested | The directory fee, testnet4 only: 20,000 sats to the store's own fee address (the head's fee key tweaked by the store id), checked on-chain by every node, for 2,016 blocks. Any wallet, exchange, or swap can pay it; the seller's node pays from its wallet when it can and again when the epoch ends. Head version 3 (`ob/seed/v3`) schedules up to 8 fee terms by block height, and each admission is judged by the terms in force at the height its fee confirmed, so a raise does not drop stores that already paid. A raise or a shorter epoch is announced 1,008 blocks ahead, anything else 288. Inside 6 blocks of a change the seller's node pays the higher fee. The fee key cannot change yet. `GET /directory/fee` gives the address, state, scheduled changes, and any refused head, shown under Store settings. Version 1 admissions (fee key plus an `OBAD` OP_RETURN) still verify. |
| Freshness and completeness | future | No sequence number or signed index. |
| Rejecting street, email, phone in public records | tested | Signing refuses store and listing text with an email, phone number, street address, PO box, or coordinates. Heuristic; decoding does not filter. |

### Client, node, and keys

| Mechanism | Status | Notes |
|---|---|---|
| Client talks only to its own node on loopback, with a pairing token | tested | Host must be `127.0.0.1`, `localhost`, or `[::1]` on the node's port (DNS rebinding); any `Origin` other than the desktop webview and `--shop-origin` is refused before routing. No route returns the token: the desktop app reads `pairing.token` and injects it into its own webview (`--no-pair-codes`); a browser shop trades a one-time code printed on the node's terminal at `POST /pair` (39 bits, 5 tries, 5 minutes, one code per 10 s). Another process of the same user can still read the file (A6). |
| Loopback HTTP limits | tested | 8 KiB head, 64 headers, 72 KiB body, exact `Content-Length`, no chunked bodies, 5 s per request; handler panics answer 500; `no-store`, `nosniff`, and `default-src 'none'` CSP on every response; 500 bodies carry no detail. Proptest over the parser and the router. Requests are served one at a time, so a stalled local connection delays others by up to 5 s. |
| Node rejects client-named destinations | tested | URL, onion, or peer keys in a request are refused. |
| Desktop app starts its own node | demo | Testnet4, through Tor built into the node (`--tor`: Arti on a free loopback SOCKS port, so no Tor install is needed and a Tor on 9050 is left alone), with Zcash (`testnet.zec.rocks`), Monero (three public stagenet onion daemons; an `xmr-daemon` file in the app data folder replaces them), and Lightning (Mutinynet signet, Megalith's LSP) on by default. The node keeps the loopback port it first got (`node.port`) while it is free. `OB_DESKTOP_DATA_DIR=<absolute path>` runs a separate instance with its own data folder, webview storage, and a file vault, for testing two nodes on one machine. macOS builds statically link liblzma so the sidecar does not need Homebrew xz at runtime; the release job fails if any shipped Mach-O still loads `/opt/homebrew` or `/usr/local/opt`. |
| Remote management from a phone or laptop (home node) | tested | Protocol v2 ([spec](home-node-protocol.md)). `--remote` publishes an Arti onion service with restricted discovery: only paired devices' Tor client keys can find it. Pairing: 80-bit one-time secret as 8 words or a QR (10 min, 4 live, pause after 20 bad proofs in 10 min), reached over an onion derived from the secret or the LAN; 4-emoji check on both screens; the owner approves on the node. Every request is signed (P-256 or BIP 340 over node id, device, time, nonce, method, target with query, body hash; ±120 s; nonces once). Watch keys may only sync. Removal drops the device and its discovery key; `--rotate` moves the node to a new onion and retires the old one when every device has moved (7-day cap). A device cannot reveal the seed, post escrow mail, use a remembered unlock, or reach `/pair` and `/home*`; spends need the passphrase and a spend ticket every time. CI uses loopback; real Tor runs by hand (pairing 16–22 s, first request after approval up to 74 s while the descriptor republishes, then 4–8 s). See [home-node.md](home-node.md). |
| Home node LAN channel and setup page | tested | `--lan`: port 8790, requests sealed to the node key (X25519, ChaCha20-Poly1305), mDNS with a random instance name, a script-free setup page with the QR and approval on first run only. Not available in Docker's bridge network. |
| Delta sync, batches, push | tested | `POST /remote/sync` returns only changed items by etag; `POST /remote/batch` runs up to 16 queued mutations once (24 h idempotency). Push is opt-in per device, content-free, sent over Tor to `--push-gateway`; no gateway is run by the project. |
| Desktop app manages a home node | tested | Its own node holds the device key and its discovery key (`home-node.obv`) and proxies `/home/proxy/*` over the LAN channel or Tor; the shop switches between the local and the home node. Two-node LAN e2e in CI; live Tor by hand. The app can also run as a home node while open (`--remote --lan` on its own node). |
| Phone app manages a home node | demo | iOS and Android app with embedded Arti (`crates/mobile-tor`), device keys in the Secure Enclave or Android keystore, emoji pairing, the LAN channel, an encrypted replica with delta sync and a mutation queue, biometric app lock, opt-in push. Android release APK checked on an emulator against a live node over the LAN and Tor; iOS checked to the device-key prompt on the simulator. CI builds an APK and a simulator app; signed builds need the credentials in [home-node-mobile.md](home-node-mobile.md). |
| Phone browser manages a home node | demo | Tor Browser with a node-issued discovery secret and access key; keys are made and used in JS. Not in CI. |
| Addresses, orders, seed, wallet, labeler follows encrypted at rest | tested | ChaCha20-Poly1305. Key in the OS keystore by default (macOS Keychain, Windows Credential Manager, Linux Secret Service); `--vault passphrase` wraps it with Argon2id (64 MiB, 3 passes) in `vault.lock`; `--vault file` keeps `vault.key` for headless runs and tests. An old `vault.key` is moved and deleted on first start in another mode. Startup refuses a group- or world-readable key, lock, or token, and tightens `.obv` files (earlier nodes wrote `addresses.obv` and `orders.obv` with the umask). |
| Wallet lock on the node | tested | Seeds sealed a second time under a random spend key, wrapped with Argon2id (256 MiB, 3 passes) of a wallet passphrase in `wallet.lock`. Starts locked; spends, escrow signing, seed reveal, and lock settings answer `423` while locked or before setup. Receive tier (xpubs, escrow mail key, store mailbox key, letter root) stays open for the watcher, addresses, incoming orders and mail, and signing letters; escrow steps that sign wait for an unlock. Auto-lock 1 to 60 min (15 default) and on sleep; persisted backoff. Each payment needs a 60 s one-time ticket bound to order, amount, fee cap, and recipient. Biometric step-up and OS screen-lock events are not wired. See [wallet-lock.md](wallet-lock.md). |
| BIP 39 seed with role paths | tested | Spend, store, escrow (`m/1984'/c'/1'/i'`), escrow mail (`m/1984'/c'/2'/0'`), store mailbox (`m/1984'/c'/3'/0'`), letter root (`m/1984'/c'/4'/0'`), scan, Monero (`m/1984'/c'/5'/0'`). |
| Own store signed with the seed's store key | tested | Profile from `store-profile.json`; BOLT 12 offer and BIP 352 code from the seed. The store key is spend tier: the last signed record is kept in `store-record.obv` and served while locked, and signed again at the next unlock if its inputs changed. |
| Vendor mailbox key bound to the signed store record | tested | Orders and escrow mail are sealed to the mailbox key in the seller's signed record. Demo store mailbox secrets are public fixtures, testnet4 only. |

### Orders

| Mechanism | Status | Notes |
|---|---|---|
| HPKE sealing of orders, replies, and escrow messages | tested | Separate `info` strings. |
| Sender authentication inside the sealed letter (`OBLT`) | tested | BIP 340 signature by a key for one conversation (one order, or one escrow and role), derived from the letter root; never the buyer's long-term key. Recipient, kind, and message id are signed. |
| Replay and sender-continuity checks on escrow mail | tested | `letters-seen` refuses a repeated message id; `letter-pins` refuses a different sender key for an escrow and role once a letter was handled. Order mail does not use it: every step an order letter triggers is idempotent, and each side pins the other's per-order key. |
| Per-order reply path in the order (`ReplyPath`) | tested | Reply key and drop id derived per order; optional reply onion field; `OBRF` frame for delivery. The buyer's base URL travels in the sealed order as `replyUrl`. |
| Mailbox storage without the store secret | tested | |
| Arti onion client and listener | library | Arti 0.48 with restricted discovery. Live dial test ignored. The node uses Arti for the home node's onion services and its client. With `--remote` that client also publishes the store onion, a reply onion per order or escrow, and with `--lightning` a Lightning onion, and carries follows, order mail, reviews, and escrow mail to other nodes' onions. `--onion` listens for sealed letters on an onion. A separate client, with its state in `tor-client/`, reaches the directory's introductions unless `--no-introductions` is set; with or without that flag it dials a directory store's own onion for its listings when that store's page is opened. |
| Order delivery buyer node to vendor node | demo | Loopback HTTP, not Tor. The order letter goes to `POST {store}/mail`, sealed to the mailbox key in the store's signed record; the seller prices it, takes a fresh address, keeps the sale in `sales.obv`, and replies at `POST {buyer}/mail/reply` with the terms, then "paid", "shipped" (tracking or the digital goods), or a decline; the buyer's "complete" goes back to the store. Receive tier, so a locked seller still takes orders. Each side pins the other's per-order key after the first letter; strangers' mail is refused. |
| Sales and fulfillment | tested | `GET /sales`, `GET /sales/{id}`, `POST /sales/{id}/fulfill`, `POST /orders/{id}/complete`. Awaiting payment, Payment seen, Paid (the seller's watcher), Shipped, Completed. The buyer's node sends a "sent" letter with each payment txid, so a seller on compact filters (no mempool view) shows "Payment sent, waiting for confirmation" before a block; only the chain makes a sale Paid. Two-node tests cover a physical and a digital sale, restarts mid-flow, an offline seller, edits, declines, and inflated terms. |
| Order messages | tested | Buyer and seller write to each other inside an order (`POST /orders/{id}/message`, `POST /sales/{id}/message`, kind `chat` in the order mail). Sealed, sender-pinned per order, queued in the order outbox for offline peers, deduplicated by message id, capped at 2,000 chars and 500 kept messages, receiver-stamped times, plain text only (never rendered as HTML, no link fetching), kept sealed with the sale/order record. Two-node round-trip, redelivery, and refusal tests; thread UI on the sale and the buyer's order. |
| Shipment tracking (AfterShip) | tested | Opt-in seller-side tracking ([tracking.md](tracking.md)): `--tracking aftership` with `OB_TRACKING_API_KEY` in the environment only. The seller's node polls at most every 6 h and only through `--proxy` (no proxy, no contact), sends only carrier + tracking number, discards checkpoint street locations, coordinates, and signer names before storage, and forwards normalized city/state/country progress to the buyer in sealed sender-pinned replies. The buyer's node never contacts a provider. Tracking records `deliveredAt` as evidence only; it does not complete an order or move escrow. Parser, coarse-location, no-proxy, buyer-validation, UI-parse, and two-node progress tests. |
| Outbox and retry | tested | Order mail uses the escrow outbox in `order-outbox/`: sealed, an idempotency key per message, retried from 2 s doubling to 15 min, dropped after 24 h. The URLs are fixed when the order is placed. |
| One letter per seller in a multi-seller checkout | tested | |
| Padding | tested | Sealed letters are exactly 2 KiB, 8 KiB, or 64 KiB; replies 2 KiB or 8 KiB. Other sizes are refused. |

### Payments

| Mechanism | Status | Notes |
|---|---|---|
| One payment per seller | tested | One recipient plus change. |
| Fresh per-order vendor address, BIP 21 URI | tested | BDK, BIP 86. |
| Chain watcher | tested | Wallet sync, order watcher, broadcast, and escrow chain checks all go through one `ChainSource`. Default: BIP 157/158 compact filters (`bip157` 0.8, Kyoto) from DNS-seeded P2P peers; filters are matched on the node and only matching blocks are fetched, each from a random peer; broadcast goes to one random peer. Filter commitments and headers are sealed in `filters/`; a peer that later serves a different filter for a checked block is refused; reorgs move transactions back to unconfirmed. 1 confirmation on testnet4, 3 on mainnet. |
| Own node | tested | `--peer HOST:PORT` uses only that node's filters (bitcoind with `blockfilterindex=1`, `peerblockfilters=1`); `--esplora URL` uses only the named servers. Neither falls back to anything; a test proves no other host is dialed. Bitcoind RPC and Electrum are not supported. |
| Public Esplora | tested | Never by default on mainnet. `--public-fallback` (default on testnet4 only) asks mempool.space/blockstream.info while no filter peer has answered, or the filter scan is behind and has not moved, for 2 minutes. With `--proxy`, each Esplora connection uses a fresh SOCKS username, so Tor gives it its own circuit. `GET /network` reports `chainBackend` (`backend`, `privacy`, `reveals`, `peers`, `scannedHeight`, `syncing`, `fallback`, `fallbackActive`) and `publicChainServer`. |
| Pay from the node | tested | Mainnet needs `--network mainnet` and `"confirm": true`. |
| Speed up a payment (RBF) | tested | `POST /orders/{id}/pay/bump` replaces an unconfirmed direct payment: the same inputs (more of the wallet's own coins if needed), the same recipient and amount, the extra fee from change. Needs the passphrase again and a `maxFeeSats` cap, not a spend ticket. The web shop shows "Speed up payment" while the payment is unconfirmed. The fee estimate is the median of recent blocks, so a run of empty blocks gives the 1 sat/vB floor. |
| Coin selection avoiding shared ancestry across one checkout | future | Own unconfirmed change is spendable, so consecutive payments can chain. |
| BOLT 12 offer | encoding only | No Lightning node answers; issuer key is the store key. Lightning direct pay uses per-order BOLT 11 invoices instead (below). |
| BIP 352 code | encoding only | No scanning. |
| Payjoin v2 | library only | Checkout does not start a session. |
| Chain queries over Tor | demo | `--proxy` also carries filter peer connections and broadcasts through SOCKS5 (P2P v1 only; peers see a Tor exit). No Arti, no onion peers. Without `--proxy`, filter peers see the IP address and which whole blocks it fetches, not which scripts it follows. |
| Compact filter limits | tested | Filters cannot find a transaction by txid, so the escrow moderator follows the funding script from the refund horizon (`refund_height - max_refund_horizon`) and holds the letter while the filters scan. No mempool view: incoming payments appear once confirmed. Fees come from recent block averages. A newly followed address is rescanned 144 blocks back; an escrow funding script from the height the moderator asks for. First sync starts at a checkpoint (testnet4 159000, mainnet 974000); testnet4 took 7.5 minutes to reach the tip from one peer. |
| Exchange rates | tested | Coinbase. Over clearnet unless `--proxy socks5h://HOST:PORT` (names resolved by the proxy); `--no-rates` makes no request. `GET /network` reports `clearnet` and a `privacyWarning`. XMR comes from Kraken's XMR/BTC ticker (Coinbase does not list XMR) on the same proxy and switch, as integer sats per XMR in `GET /rates` `xmr`. `--fixed-rates BTCUSD=N,ZECUSD=N[,XMRUSD=N]` (testnet4 only, refused on mainnet) takes the price of 1 BTC, of 1 ZEC and optionally of 1 XMR in whole dollars from the command line, so a node can price orders without the network, for tests and offline use: no rate server is asked, the price never goes stale, XMR has no price unless `XMRUSD` is given, and `GET /rates` reports `"source": "fixed"`. Live answers carry `ageSecs` (for XMR and ZEC, the older of their own answer and the BTC one); the wallet shows a price older than 15 minutes with its age and none older than a day. |

|---|---|---|

### Code notes the paper leaves out

- The escrow crate's signed-terms wrapper uses the magic `OBTS`; `OBST` is only the store record.
- A buyer's first order letter cannot prove who the buyer is: by design the buyer has no identity to prove. Letters are signed by per-conversation keys instead of HPKE Auth mode, which would need the sender's key in the clear.
- The crate supports per-order keys tweaked by an order secret; the node derives per-order keys from the seed instead.
- Exchange rates come from Coinbase over clearnet unless `--proxy` is set. Chain data comes from compact filters; public Esplora is asked only with `--esplora` or `--public-fallback`. The desktop app has no proxy, peer, or fallback setting yet.
- The paper describes bitcoin payments only. Monero and Zcash direct pay are additions of this implementation; escrow stays bitcoin-only.
